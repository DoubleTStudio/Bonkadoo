# Interaction implementation notes and unresolved design-to-code work
Puzzle solutions are authored as **two alternative interaction recipes** with `option.<puzzle>.<a|b>` targets. The scene input adapter must expose `input.<puzzle>.choice` as a **transient request-context predicate**, never as a permanent saved world flag. Update `flagEquals` resolution to consult transient input namespace only for `input.*` keys; reject persistent writes to `input.*`. When the player selects a recipe through scene props/NPC choices, the adapter emits a request with the corresponding option ID. Real scene authoring must translate recipe steps into discoverable visual affordances; never show 'option.a' to the player.

Before shipping any chapter, replace generic success/failure dialogue seeds with authored comedic reactions, verify solution distinctness (not merely option aliases), build actual scene graphs and tests for reachability. The seed rules are executable *structural examples*, not proof that all 45 puzzles are fun or fair.

Potential design risk: the current DSL models high-level completion choices, not intermediate object state. During M1, add typed step-level predicates (`requestVerb`, `requestTarget`, `requestSource`) and intermediate events through ADR + tests, then regenerate puzzle content to use real interaction traces. Do not claim full puzzle implementation until this is complete.
